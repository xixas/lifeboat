Empty folders and backup progress

The real-account test of the setup wizard ended with "Failed (exit 1)" on the very first backup, only because the test laptop's Pictures folder was empty. That will happen to anyone with a fresh laptop, so it gets fixed before 0.4.0. Your second ask, a checklist instead of raw logs, is planned here too.

What happened

INFO : hello.txt: Copied (new) INFO : notes/n1.md: Copied (new) documents rc=0 pictures: refusing to sync: source …/a/Pictures is missing or empty (unmounted drive or typo?) — nothing was changed pictures rc=2 INFO : id_test: Copied (new) ssh-keys rc=0 manifest rc=0 probe rc=0
  1. The wizard offers every standard folder that exists, switched on (setup.py:337 suggest_folders). An empty Pictures qualifies.
  2. The engine refuses any job whose source has no files (engine.py:220, has_files at :133) with rc=2. That guard exists so an unplugged drive can't make the backup look empty and get mirrored as deletions.
  3. One refused job makes the whole run "Failed". Documents, SSH key, manifest and passphrase probe all succeeded.

A. Empty-folder fix

ships in 0.4.0

The engine tells "empty because nothing is here yet" apart from "empty because something went wrong" by also looking at the backup side. A job is only skipped when the folder exists, holds no files, and its backup copy is empty too. Syncing nothing over nothing can't lose data. Every other case keeps today's refusal.

Has filesanythingBacked upNormal run, unchanged.
Exists, emptyMissing or empty (lsf rc 3, or rc 0 with no output)Skipped: nothing to back up yetNew. Counts as OK, so the run reports success.
Exists, emptyHolds filesRefusedLooks like an unmounted drive or wiped folder. Same as today.
Exists, emptyCan't tell (offline, auth error, any other rc)RefusedFails closed. A listing error must never count as "empty" (Fable #1).
MissinganythingRefusedA typo'd path would otherwise be silently skipped forever.

Engine

In run_backup: before refusing, list the destination (rclone lsf <dest> --max-depth 1). The job result gets "skipped": true with rc 0, so status() (engine.py:367), last-run.json and the Backups page can say "not backed up yet" instead of "OK" (Fable #2). The log line reads pictures: skipped — folder is empty, nothing to back up yet.

Wizard

Empty folders stay on, so photos added next month are backed up without revisiting settings. Their row subtitle becomes "Empty — backed up once you add files" (via with_size, setup.py:372), so the choice explains itself.

Also in 0.4.0

The Recovery Kit page scrolls (the separator line above "Set Up Backup"). Fix: add libadwaita's compact style to its Adw.StatusPage (wizard.py:244), the way pages.py:70 already does.

Tests (written first)

  • empty source + missing dest → skipped, rc 0, run ok
  • empty source + non-empty dest → refused, rc 2, nothing synced
  • empty source + dest listing fails (rc 1) → refused, rc 2
  • missing source → refused, rc 2, no dest listing
  • status() exposes skipped; suggest_folders' subtitle for size 0

Then rerun the real-account test (fresh sandbox, empty Pictures kept on purpose). Done = the first backup reports success with Pictures skipped, and restore + check pass.

How the window learns progress

Two separate pipes instead of today's merged one (STDERR_MERGE, window.py:256), so an rclone line that happens to start with { can never be mistaken for an event (Fable #5). --json already sends human output to stderr (cli.py:30), so this follows an existing convention. --json stays a single document at the end.

Widgets

  • Adw.ActionRow per job, plus one "Finishing up" row for manifest + probe.
  • Suffix: the existing spinner() (widgets.py:22), then a Gtk.Image with the success / warning / error style class.
  • The Log page is today's TextView, kept as-is and filled from stderr. On failure the dialog stays on Progress with the failed row expanded. It never drops you into the raw log.
  • "Copied N files" is counted from rclone's per-file Copied lines the engine already streams. 0 reads "Already up to date".

D. A proper sign-in page in the browser

0.4.0

After Google sign-in the browser lands on rclone's bare page: "Success! All done. Please go back to rclone." The user never heard of rclone. rclone authorize takes --template <file> (a Go template, confirmed in rclone authorize --help), so Lifeboat ships its own page and passes it in setup.py:136.

⛵
You're Signed In
Lifeboat can now reach your Google Drive. Go back to Lifeboat to finish. You can close this tab.
✓ Connected to Google Drive
  • Centered card: the Lifeboat icon (inline SVG from data/io.github.xixas.Lifeboat.svg), a title, one line on what to do next. Light and dark follow the system.
  • Failure variant: "Sign-in Didn't Work", rclone's error name and description in small text, "Go back to Lifeboat and try again."
  • Self-contained: inline CSS and SVG, no web fonts, no external requests. The page is served from 127.0.0.1.
  • Shipped inside the Python package, so install.sh, the tarball and the RPM all carry it. A test renders the template through rclone's own Go template parser to catch syntax errors.

Risks and what's parked

Wrong passphrase looks empty. A crypt destination listed with the wrong passphrase returns rc 0 and no names. Worst case is a false "Nothing to back up yet" for an empty folder. Nothing is synced, so no data is lost. The passphrase probe in the same run still flags the real problem.
Parked, not new: has_files ignores a job's excludes. A folder holding only excluded files still syncs and moves the whole backup into the "old versions" folder. It can be recovered for keep_days. This is tracked as a follow-up, not part of 0.4.0.
